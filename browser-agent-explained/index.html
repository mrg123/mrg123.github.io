模型从来没有看见过那张网页

浏览器智能体（browser agent）常被描述成「AI 自己上网」。但它真正做的事要朴素得多： 把页面压缩成一段文本或图片交给模型，模型回一个动作， 然后重复。理解这个「投影—动作」循环，就能推导出它的全部能力边界。 本文按 模型 / harness / 浏览器 三层拆开，一直讲到 CDP 消息。

00 / 定义

它是什么，以及那个反直觉的关键点

先用严格的一句话把边界划清楚，再引入贯穿全文的洞察。

定义（原文表述）

浏览器智能体是一种软件：它用一个 AI 模型，朝着某个目标去操作网页浏览器。你描述任务，它自己去打开页面、导航、选择动作，并在继续之前检查结果。因为能适应意外变化并从错误中恢复，它特别适合无法预先写死步骤的流程。

贯穿全文的洞察：模型并不"看见"浏览器。浏览器是活的、有状态的、持续变化的； 而模型只能读 token。所以中间必须有一层做翻译——把页面投影成文本或图像，再把模型的 决定翻译回鼠标键盘事件。这一层叫 harness。投影方式是所有取舍的源头： 投影得准，它就聪明；投影失真，它就自信地做错事。
输入

一句自然语言目标

「找出这个仓库的 star 数」「把这个月的发票下载下来」。没有选择器，没有步骤，只有意图。

过程

循环里的判断

每一步都要看当前页面、决定点哪里或输入什么、然后确认这一步是否奏效。

输出

一个被校验过的结果

结构化数据、一个已提交的表单、或一份带引用的答案。注意：跑完不等于成功。

01 / 架构

三层：模型、harness、浏览器

原文把浏览器智能体的组成拆成三部分。点击任意一层展开它的职责、输入输出与典型故障点。

Layer 1 · 决策

Model（模型）

读页面投影 → 决定下一步做什么。整条链上唯一「会思考」的部分。
›
它负责什么

根据任务和当前页面，选出一个动作。它拿到的页面信息可能是文本、结构化数据，也可能是截图——由 harness 决定。

输入 / 输出
  • 输入：系统提示（含工具定义）+ 任务 + 当前页面投影 + 历史动作记录
  • 输出：一个工具调用，例如 click(index=7)、type(text="…")、done(result=…)
典型故障

选错元素、把页面上的诱导文字当成用户指令（提示注入）、在没真正完成时宣称完成。这类失败表现为「它很自信但结果是错的」。

Layer 2 · 控制

Harness（执行框架）

持有循环、拼装上下文、执行工具调用、把结果回灌给模型、在超限时刹车。
›
它负责什么

让循环继续转下去：给模型上下文，运行模型请求的工具，把结果传回去供模型决定下一步。它是唯一同时看得见「模型」和「浏览器」的一层，也因此承担了绝大多数工程复杂度。

输入 / 输出
  • 输入：模型的动作请求；浏览器的页面状态
  • 输出：给模型的投影；给浏览器的协议指令
必须实现的四件事
  • 投影：把页面转成模型能吃的形式（见下一节）
  • 循环：观察 → 决策 → 执行 → 校验
  • 限额：时间、步数、成本三个维度的硬刹车
  • 人在环：遇到登录、验证码、敏感动作时挂起等人

原文提到 Browser Use 的 Browser Harness 走了一条变体路线：它把浏览器能力直接挂到已有的编程智能体上，让那个智能体在运行过程中自己写缺失的辅助函数，而循环仍由编程智能体的 runtime 管理——相当于不给模型新框架，只给它新工具。

Layer 3 · 状态

Browser（浏览器）

真正加载网站，持有标签页、cookie、登录态；通过协议被外部驱动。
›
它负责什么

加载网站，并跟踪标签页、cookie 和登录状态。它不是「被模拟」的——它是一个真浏览器在真渲染。这是浏览器智能体相对纯 HTTP 抓取的根本优势：它继承了一个真实人类会话的全部上下文。

怎么被驱动
  • 通常通过浏览器协议控制：Chrome DevTools Protocol (CDP) 或 WebDriver BiDi
  • 也可以通过 MCP server 暴露成工具，例如 Playwright MCP 把 Playwright 包装成模型可调用的工具
  • 服务器场景常用无头模式：没有可见窗口，但依然渲染页面、依然能截图
典型故障

被反爬系统质询或封禁、会话过期、多因素认证需要人介入。这一类失败换更强的模型也解决不了——因为瓶颈不在推理，而在访问权。

为什么必须分成三层？因为三者的失败模式完全不同，而且修法不同。模型变强只改善第一层；harness 写好限额只改善第二层；买住宅代理只改善第三层。 把这三件事混成一句「AI 上网」，就没法定位问题。
02 / 循环

本质就是一个循环

原文的说法很直接：「浏览器智能体基本上就是一个花哨的循环。」这句话是整个架构的骨架。

Observe

观察

把当前页面投影成模型可读的形式，page = observe()

Decide

决策

模型根据投影选一个动作，action = pickAction(page)

Act

执行

通过协议把动作变成真实事件，result = execute(action)

Verify

校验

检查这一步是否奏效，goalReached = checkResult(result)

未达目标回到观察
loop.pseudo原文伪代码
while (!goalReached) {    page = observe()    action = pickAction(page)    result = execute(action)    goalReached = checkResult(result)}

为什么它必须是循环，而不是一次调用

因为网页是有状态且异步的。这是新手最容易低估的地方，也是绝大多数"明明点对了却没生效"的根因。

异步问题后果harness 该怎么处理
命令成功 ≠ 页面就绪导航指令返回了，页面可能还在加载；此时读到的内容是旧的等导航事件（如 Page.loadEventFired）并加超时，而不是等命令响应
页面随时会变菜单弹出、弹窗盖住表单、新结果替换了刚才读的内容每次动作后重新观察，不复用上一轮的投影
旧引用会失效导航会销毁 JS 执行上下文，之前拿到的对象引用全部作废不要缓存元素句柄，用"重新查询"代替"持有引用"
单页应用延迟渲染文档加载完成不代表内容就绪等到你真正需要的那个元素出现，而不是等 load
停止条件同样属于架构的一部分。原文明确要求：harness 应当在触及时间、步数或成本上限时终止运行。没有这三个刹车，一个误判的循环会持续烧钱——因为每多转一圈就多一次模型调用和一段浏览器时长。

人在环不是退让，是设计

循环允许随时挂起等人：让人登录、补一个缺失信息、或批准一个敏感动作。 把它当成架构的一等公民，比事后补一个"异常处理"要可靠得多。

03 / 感知

页面怎么变成模型能读的东西

这是整个架构里最关键的工程决策。原文列出两条路，且可以同时使用：结构化数据，或截图。

路线 A · 结构化

DOM

文档对象模型：表示页面上的元素与文本。它是浏览器解析标记后形成的树。

优点信息最全，能拿到文本、属性、层级
缺点体积极大、噪声极多，塞进上下文很贵
DOM.getDocument / DOM.querySelectorAll
典型失效：页面结构语义混乱，或用了大量无语义 div，模型无法判断哪个能点。
路线 B · 结构化（语义）

无障碍树

浏览器基于 DOM 构建的辅助树，供屏幕阅读器等辅助技术使用。每个对象有四个关键属性。

name怎么称呼它（如「搜索」）· role它是什么（按钮 / 导航 / 列表）
state它的状态（已勾选 / 已展开）· description补充说明
Accessibility.getFullAXTree
核心优势：可以按名字和角色识别控件，不必靠猜它在图片里的位置。
路线 C · 视觉

截图

让具备视觉能力的模型直接读渲染后的页面，并输出坐标去点击。

优点对 canvas 等无标注的可视界面有效
缺点小控件难点准；截图缩放后细节丢失
Page.captureScreenshot → Input.dispatchMouseEvent
典型失效：目标控件只有几个像素宽，或需要精确输入文字。
把两种路线对照着看：无障碍树回答的是「这是什么、叫什么」，截图回答的是「它在哪、长什么样」。 前者适合表单、按钮、链接这类有语义的控件；后者适合画布、图表、自绘 UI。实践中通常先取无障碍树， 遇到解释不了的部分再退回截图。

一个容易被忽略的性能代价

CDP 的 Accessibility.enable 官方说明里写着：启用无障碍域后，AXNodeId 才能在多次调用之间保持稳定； 但这会给页面带来性能开销，直到你把它关掉。也就是说，"让智能体看得更清楚"是有运行时成本的—— 这属于典型的架构权衡，不是免费的开关。

维度DOM无障碍树截图
定位方式选择器 / 节点 ID角色 + 名称像素坐标
上下文体积很大较小中等（含图像）
语义理解需模型自己推断直接给定依赖视觉能力
自绘 / canvas几乎无用几乎无用可用
精确文字输入好好差
小控件精度高高易失准
04 / 协议

再往下一层：动作是怎么变成真事件的

模型输出的是文本。文本要变成真实的鼠标点击和键盘输入，中间必须有一条被广泛实现的协议通道。

方案是什么跨浏览器谁在用
CDP
Chrome DevTools Protocol		 Chromium 系浏览器的底层调试 / 控制协议。Chrome DevTools 本身就用它和浏览器通信；也是 Playwright、Puppeteer 的底座。 仅 Chromium 绝大多数浏览器智能体 / 自动化库
WebDriver BiDi W3C 工作草案（Working Draft）阶段的双向协议，目标是跨浏览器提供类似的自动化能力。 是 需要多浏览器覆盖的场景
MCP
Model Context Protocol		 不是浏览器协议，而是把浏览器能力包装成模型可调用工具的中间层。底层仍跑真实自动化（如 Playwright MCP 底层就是 Playwright）。 取决于底层 已有编程智能体想"外挂"浏览器时

CDP 的三个核心概念

概念 1

Domain（域）

把能力分组。常用几个：

Page 导航、截图
Runtime 执行 JavaScript
DOM 节点查询、盒模型
Accessibility 无障碍树
Input 鼠标 / 键盘事件
Network 请求与响应
概念 2

Target（目标）

任何可以被调试或控制的东西：一个页面、标签页、iframe、worker。每个 target 一般有 targetId。

要操作某个标签页，先拿到它的 target，再附加上去。
概念 3

Session（会话）

你与某个特定 target 通信的连接。附加成功后 Chrome 给你一个 sessionId，用于指明后续命令发给谁。

Target.attachToTarget
结构可以这样记：浏览器下面挂多个 target，每个 target 对应一条 session，命令都在 session 里发。 所以「一个标签页点不动」的第一反应应该是检查 session 有没有附加到正确的 target，而不是怀疑模型。

消息长什么样

CDP 用的是改造过的 JSON-RPC。命令带 id、method 和可选的 params； 响应重复同一个 id 并带上 result 或 error； 事件只有 method，没有 id——靠这个区分"这是回我的"还是"这是浏览器自己发生的"。

cdp / 命令 → 响应 → 事件真实消息格式
// 1) 命令：带 id，等待匹配的响应{ "id": 2, "method": "Page.navigate",  "params": { "url": "https://example.com" } }// 2) 响应：id 对上了，说明这是命令回执{ "id": 2, "result": { "frameId": "A7789DDD…" } }// 3) 事件：没有 id，是浏览器主动通知{ "method": "Page.loadEventFired",  "params": { "timestamp": 181921.758 } }
这张图里有整个架构最重要的一条纪律：收到 id: 2 的响应，只说明命令被接受了，不说明页面加载完了。 真正代表"就绪"的是那条没有 id 的 Page.loadEventFired。所以必须先开监听、再发导航， 并加上超时。顺序错了就会稳定地读到旧页面——一个非常经典的时序 bug。

三种感知路线对应的真实命令

05 / 实现

把它拼起来：一个最小骨架

把前四节合起来，一个可运行的浏览器智能体只需要大约这些。下面是结构示意，不是完整可运行代码——但每一行的职责都是真实的。

mini_agent.py骨架示意
import json, asyncio, websocketsclass MiniAgent:    def __init__(self, ws_url, llm, task, max_steps=25):        self.ws_url   = ws_url        self.llm      = llm        self.task     = task        self.max_steps = max_steps   # 刹车之一：步数上限        self._id = 0    async def send(self, ws, method, params=None):        # CDP：命令带 id，响应回来时靠 id 配对        self._id += 1        msg = {"id": self._id, "method": method}        if params: msg["params"] = params        await ws.send(json.dumps(msg))        while True:                       # 跳过无 id 的事件，直到等到响应            r = json.loads(await ws.recv())            if r.get("id") == self._id:                return r    async def observe(self, ws):        # 投影：取无障碍树，而不是整个 DOM        await self.send(ws, "Accessibility.enable")        tree = await self.send(ws, "Accessibility.getFullAXTree",                                {"depth": 8})        return self.flatten(tree)     # 压成「角色+名字」的紧凑列表    async def act(self, ws, a):        if a["type"] == "click":            # 无障碍节点带 backendDOMNodeId → 盒模型 → 中心点            box = await self.send(ws, "DOM.getBoxModel",                                     {"backendNodeId": a["nodeId"]})            x, y = self.center(box)            for t in ("mousePressed", "mouseReleased"):                await self.send(ws, "Input.dispatchMouseEvent",                    {"type": t, "x": x, "y": y,                     "button": "left", "clickCount": 1})        elif a["type"] == "type":            await self.send(ws, "Input.insertText", {"text": a["text"]})    async def run(self):        async with websockets.connect(self.ws_url) as ws:            for step in range(self.max_steps):                page   = await self.observe(ws)          # 1 观察                action = self.llm.decide(self.task, page)  # 2 决策                if action["type"] == "done":                    return action["result"]                await self.act(ws, action)                # 3 执行                await asyncio.sleep(0.3)                # 4 等页面稳定后再观察        raise RuntimeError("达到步数上限仍未完成")
这段骨架故意留了三个坑，正是真实实现必须补的： ① sleep(0.3) 是幼稚的等待，生产环境要等事件或特定元素； ② 没有成本与时间刹车，只有步数； ③ 没有对页面内容做不可信输入处理，存在提示注入风险。把这三个补上，才算接近可用。
不想从协议写起？原文给了三条现实路径： ① 用开源库 browser-use（Python / TypeScript，MIT）——uv add browser-use 后构造 Agent(task=…, llm=…, browser=…)，调 agent.run() 取 history.final_result()； ② 用托管 API，只提交任务、取回结果； ③ 如果你已经在用编程智能体，给它加浏览器工具可能就够了——它的 runtime 本来就在管推理循环。
06 / 选型

Agent、脚本、API：先问该不该用智能体

这是最省钱的一节。很多被做成智能体的任务，本来用 API 或脚本会更快、更便宜、更可靠。

原文的判断顺序

服务有可用 API 就用 API；没有 API 而流程可预测，就用脚本（Playwright / Selenium / Puppeteer）；只有当下一步取决于页面上出现什么、步骤无法预先写死时，才用智能体。

维度API脚本智能体
决策性质无（直接取数据）确定性：同样输入 → 同样决策随机性：同样任务可能走不同路径
网站改版通常无感要改代码往往能自己适应
单次成本最低低高且不可预测
结果可重复性高高低
适合有接口的一切每周固定下载同一份报表在陌生网站里找资料、结构各异的表单
"随机性"是架构属性，不是缺陷。脚本和常规 API 流程用确定性规则；智能体的决策是概率性的。 这既带来适应性，也带来不可重复性。原文还提了一个很实用的观点：智能体是极好的原型工具—— 你可以先把流程跑通，再去判断哪一段值得改写成确定性脚本。

三个必须一起读的限定条件（原文明确交代）： ① 占比是「归入该类别的运行数 ÷ 数据集全部运行数」，分母包含那 15% 未分类； ② 统计里同时混入了端到端任务与支撑性步骤——「绕过登录」18% 是步骤，不是目标； ③ 这些数字描述的是人们跑什么，不是任务成功率。 把它读成"登录最难"是误读，更准确的说法是"登录是最高频的拦路环节"。

08 / 失效

五类限制，分别落在哪一层

原文把限制列成清单。真正有用的做法是把每条限制映射回架构层——这样看到故障现象，就能直接推断该修哪里。

L3

被网站封禁 访问权

机器人管理系统会质询或拦截自动化流量，速率限制会约束请求频率；有的站点允许公开浏览，却在登录或结算处加紧检查。

诊断：若错误是 403 / 质询页 / 验证码，换更强的模型没有用——瓶颈在浏览器与网络身份，要动的是代理、指纹、会话与节奏。

L2

认证与会话过期 状态

会话会过期，多因素认证需要人来输入。复用已认证会话来减少重复登录，但流程仍要处理"会话已失效"。

诊断：表现为突然被弹回登录页。设计上必须内置挂起等人的分支，而不是让智能体自己猜密码。

L1

结果错误或不完整 决策 / 校验

可能选错商品、漏填必填项、或在尚未保存时就报告完成。「跑完没有报错」不等于成功。重试还可能造成重复下单、重复投递。

诊断：这一层最危险，因为失败是静默的。原文给的纪律：重试前先查保存记录或确认页；做提取时把返回值与源页面对照——JSON 合法不等于数据正确。

L1′

提示注入 信任边界

页面里可以埋入指令，试图把智能体从你的任务上引开。这是把不可信内容喂进决策层的经典后果。

诊断：应对方式不是"教模型别听"，而是架构隔离：把页面内容当不可信输入、限制智能体能访问的账号与动作、对敏感动作强制人工批准。原文诚实地加了一句：这些措施降低风险，但不能消除。

L2′

成本不可预测 控制

因为跑在 LLM 上，你无法预知一个任务要一步、两步还是很多步。按用量计费时，更多模型调用与浏览器时长直接推高成本；失败后重跑还要再付一次。

诊断：这是控制层问题，靠限额与统计解决，不是靠省钱提示词。下一节给出正确算法。

这张映射表的价值：看到现象就能定位层级。被封 → L3；被弹回登录 → L2；结果对但不对 → L1；页面里有奇怪指令 → L1′；账单失控 → L2′。 把五条限制平铺成清单只能记住"有风险"，映射到层才能修。
09 / 成本

别用"单次运行成本"衡量它

原文给了一个很实用的成本口径，能避免绝大多数自欺。

单任务成本  =  全部尝试的总花费（含失败与重试）
已验证成功的任务数
人工复核耗时需单独计列，不要摊进这个分子——否则会掩盖真实的人力成本。
常见算法问题
只算成功那一次的花费系统性低估。失败与重试的成本被隐藏
按"每次运行均价"报预算方差极大，均值没有预测力
只统计 API 费用漏掉浏览器时长（云浏览器按小时计费）
总花费 ÷ 已验证成功数唯一能用来做决策的口径
为什么必须引入"已验证"这个词：因为第 8 节的 L1 失效是静默的。如果不校验就计数， 分母会把"报告成功但其实没保存"的运行也算进去，成本瞬间被系统性美化。 成本统计与结果校验是同一件事的两面。
10 / 起步

从一个只读任务开始

原文给的上手路径很克制，值得照做——因为智能体的失败模式是静默的，先用低风险任务建立直觉。

  1. 先选一个只读任务

    例如采集商品价格。不要一上来就做下单、投递、付款这类有副作用的任务。

  2. 把边界写成明确约束

    规定：允许访问哪些页面、必须返回哪些字段、什么算成功。这三件事写清楚，比优化提示词更有效。

  3. 上三个刹车

    运行前设定时间、步数、成本上限。（若用开源库，对应 max_steps 一类参数。）

  4. 选执行方式

    托管智能体只管提交任务与取回结果；自建则用开源库配本地或云浏览器。如果已有编程智能体，先试"加浏览器工具"这条最轻的路。

  5. 重复跑，并与源页面比对

    记录四个指标：已验证完成率、耗时、总成本、人工修正次数。单次成功没有意义，重复性才是信号。

  6. 确认稳定后再扩张

    只在理解了"它在哪里需要人帮忙"之后，才增加更多站点或任务。

一个容易踩的坑：原文特别提醒——远程浏览器本身只提供浏览器环境， 你的智能体或脚本仍需自己控制它。买了一个云浏览器，不等于买到了一个智能体。这两件事经常被混为一谈。
11 / 小结

三句话收束

结构

三层各司其职

模型决定做什么，harness 维持循环并翻译，浏览器持有真实会话。三者的失败模式互不重叠，所以要分开诊断。

机制

一切都是投影

模型只能读 token。它的"视力"完全取决于 harness 把页面投影成 DOM、无障碍树还是截图。投影决定上限。

纪律

跑完 ≠ 成功

异步让"命令成功"变得不可信，概率性让"同样任务"变得不可复现。所以必须校验结果、必须设限额、必须按已验证成功算成本。
